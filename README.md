## 一、问题

大多数创业复盘散落在朋友圈长图、知乎回答和关停的公众号里。
结果是三个问题：

- **搜不到** —— 没有统一结构，无法按行业、原因检索
- **传不下** —— 一篇长文只服务一个作者当下的倾诉欲，不服务下一个人的检索
- **更没人看** —— 发布即沉底，没有任何分发机制

这不是「记录不够多」的问题，是**没有结构、没有检索、没有分发**的问题。

## 二、机会：调研结论

我做了真实竞品调研（见 [完整调研](docs/product/竞品分析.md)），三条结论：

**1. 需求在海外被验证过，形态可复制。**
[Failory](https://www.failory.com) 用结构化数据库收了 400+ 条失败创业记录，
拿到 4 万+ 邮件订阅，访谈了 200+ 位失败创始人。**它证明这个形态成立。**

**2. 国内没有形态一致的产品，但也没有需求验证。**
中文的失败复盘 100% 是长文，分布在知乎、公众号、人人都是产品经理。
没人做不等于机会，也可能说明结构化在中文语境里不成立。

**3. 行业教育已经完成，产品化没人做。**
CB Insights「42% 的创业公司死于没有市场需求」这个数字在中文互联网早已广泛流传。
认知有了，只是没有人把它做成可检索、可比较的产品。

### 调研中最重要的一个发现

CB Insights 在 2024 年用 431 家失败公司重做了统计，结论变了：

> **「资金耗尽」在 70% 的案例里出现，但它几乎总是最后死因，不是根本问题。**
> 真正的根因首位是产品市场匹配失败（43%）。

这直接暴露了原设计的致命缺陷：`failureReason` 是自由文本，
**70% 的复盘会写成「钱烧完了」**——数据看起来很充实，但完全无法回答
产品要回答的问题。一份全是死因的失败数据库，检索价值接近于零。

所以数据模型改成了**「根因 + 死因」两层结构**，
根因使用 CB Insights 的受控词表（13 项根因 / 12 项死因，
用户已经认得这些词，降低学习成本）。

这个改动不是我在设计文档里想出来的，是竞品调研逼出来的。

## 四、取舍

产品工作的主体是决定**不做什么**。四个最重要的判断：

| 判断 | 理由 |
|:--|:--|
| **根因强制，死因也强制** | 根因是可聚合的价值。放松根因等于放弃整个产品；只留根因不留死因，「资金耗尽」就会重新吞掉整张表 |
| **不做模板、不做草稿** | 结构化字段已经抬高投稿门槛，再加编辑态会把供给侧彻底堵死 |
| **咨询与 VIP 不做首页入口** | 早期没有转化数据，提前铺商业化会污染产品定位和北极星指标 |
| **砍掉广告变现** | 与北极星指标直接冲突；目标用户不是泛围观者；早期无流量，但广告是永久的体验债 |

一个已知的**错误风险**必须说在前面：

> 结构化是这个产品最大的风险，不是它最大的优势。
> 它换来可检索性，代价是把作者想写的「一个故事」压成十个字段。
> 如果投稿转化率极低，说明这个取舍是错的。
> **这是上线后第一个要测的东西**（用户旅程 H5，证伪线 2%）。

## 五、怎么算成功

完整定义见 [指标体系](docs/product/指标体系.md)。

> **北极星：月度有效复盘被阅读数（MVPR）**
> 统计月内根因字段非空、且被阅读至少一次的复盘记录条数。

选它的理由：这个产品的问题出在「没人看」，所以指标必须盯**消费侧**。
发布数是驱动指标，不是北极星——1000 条无人阅读的记录，价值为零。

指标内建质量门槛（根因非空）。没有这个门槛，一堆空洞记录被点开也算数。

同样重要的是明确**不追踪什么**：不追注册数（没有注册动作）、
不追停留时长（消费形态是「检索→拿到判断→离开」，停留短可能恰恰是做对了）、
不追 PV 作为成功指标。

## 六、埋点

**零埋点是原稿最硬的技术缺陷。** 指标体系写完却没有采集能力，等于没有。

现已实现 **19 个事件、5 组**（消费／互动／供给／商业／诊断），
走独立云函数通道上报，事件字典见[埋点方案](docs/product/埋点方案.md)。

`events` 集合设为**客户端完全不可写**——因为当前架构允许客户端直接写库，
若埋点集合同样开放，任何人打开调试器就能伪造「我读了 1000 篇」，所有指标同时失效。

| 组 | 事件数 | 服务 |
|:--|:--:|:--|
| 消费 | 5 | 阅读渗透率、人均月阅读条数、搜索使用率与成功率 |
| 互动 | 5 | 致敬率、评论率、分享率 |
| 供给 | 4 | **供给转化率**（H5 的唯一检验手段）、内容结构完整率 |
| 商业 | 4 | 咨询下单转化率、VIP 转化率 |
| 诊断 | 1 | `debug_entry_click`——**有量就是 bug**（正式版期望值为 0） |

**当前状态：已写入代码，但未运行时验证**——项目未部署，只做了
语法、JSON 合法性和事件名一致性检查（`check.ps1` 第 9 项做双向校验：
客户端白名单 ↔ 服务端白名单 ↔ 实际调用点，三者必须一致）。

诚实列出来，因为「知道自己缺什么」本身就是能力：

| # | 缺口 | 影响 |
|:--|:--|:--|
| 1 | `events` 集合**没有任何查询界面** | 数据进了库但看不到，北极星指标目前算不出来 |
| 2 | 无内容审核、举报、评论删除机制 | 涉及企业与个人负面判断，风险由平台承担 |

### 数据库（11 个集合）

按**谁能写**分组，而不是按功能分组——这是本项目最重要的一张表：

| 集合 | 用途 | 客户端可写 | 关键字段 |
|:--|:--|:--:|:--|
| `projects` | 项目档案 | 仅创建者 | `causeRoot` `causeSymptom` `views` `likes` `status` |
| `users` | 用户与权益 | 仅创建者 | `isVip` `projectsCount`（**均只能由云函数写**） |
| `comments` | 评论 | 仅创建者 | `projectId` `content` `nickname` |
| `favorites` | 收藏记录 | 仅创建者 | `projectId` |
| `likes` | 点赞记录 | **否** | `projectId`（与计数同事务） |
| `events` | 埋点事件 | **否** | `event` `uid`（哈希）`props` |
| `project_views` | 阅读去重 | **否** | `_id` = 用户+项目+自然日 |
| `notifications` | 站内通知 | 仅本人改已读 | `recipientId` `type` |
| `orders` | VIP 订单 | **否** | `status` 恒为 `pending` |
| `advisors` | 导师 | **否** | `price`（服务端定价的唯一来源） |
| `consultations` | 咨询记录 | **否** | `originalPrice` `price` `discountApplied` |

### 三类被修掉的「静默失效」

这三处的共同特征：**界面上一切正常，功能从来没工作过。**

| 现象 | 根因 | 现在 |
|:--|:--|:--|
| 浏览量永远是 0 | 客户端 `update({views: _.inc(1)})` 被「仅创建者可写」拒绝，错误被 `try/catch` 吞成一行日志 | 计数移到 `recordInteraction` 云函数，绕过集合权限；失败会直接报错 |
| 点赞数会漂移、甚至变成负数 | 先插文档再更新计数，两个请求不是事务；`_.inc(-1)` 在计数错乱时能减成负数 | 计数与文档在同一事务内变更，带下限保护 |
| 任何人可以给自己打 VIP | `users` 集合客户端可写，调试器里一句 `update({isVip:true})` 就能提权，而 `isVip` 是咨询 8 折的唯一判据 | 资料修改走 `updateProfile`，只接受 3 字段白名单；`isVip` 只由支付回调写 |

### 快速开始

1. [微信开发者工具](https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html)
   导入项目，填入你的 AppID（改 `project.config.json`）
2. 开通云开发，记下环境 ID（改 `miniprogram/app.js` 的 `wx.cloud.init` 的 `env`）
3. 云开发控制台新建 **11 个集合**：
   `projects` `users` `comments` `likes` `favorites` `events`
   `project_views` `notifications` `orders` `advisors` `consultations`
4. **按表设权限，不要全用同一套**：`events` / `likes` / `orders` /
   `advisors` / `consultations` / `project_views` 设为客户端不可写，
   `notifications` 按 `recipientId` 过滤。详见
   [部署指南 §五](docs/部署指南.md#五配置数据库权限)
5. 右键 `cloudfunctions/<函数名>` → 上传并部署：云端安装依赖（**12 个函数**）
6. 给 `initTestData` 配环境变量 `ALLOW_SEED_DATA=true`（否则演示数据初始化会被拒绝）
7. 编译运行。首页为空时 → 我的 → 底部调试工具 → 初始化测试数据

完整图文步骤见 [部署指南](docs/部署指南.md)。

### 自检与 CI

```bash
npm run check    # 15 项，见下
```

其中 6 项是**防「文档声称 A、代码里是 B」**的：

| # | 检查 | 挡什么 |
|:--|:--|:--|
| 9 | 埋点事件名**双向**校验 | 客户端与服务端白名单不一致 → 事件被静默丢弃 |
| 10 | 云函数交叉校验 | 代码调了不存在的函数 / 存在没人调用的孤儿函数 |
| 11 | 两份 `schema.js` 哈希比对 | 云函数按目录独立部署，改一份忘另一份 |
| 12 | 集合清单 ↔ 数据模型 | 少建集合 → 部署后 `collection not exists` |
| 13 | 部署指南 ↔ 云函数与集合 | 照文档部署会漏东西 |
| 14 | README 数量声明 ↔ 实际 | 「README 少写了四个云函数」这类最伤可信度的偏差 |

CI 每次 push 与 PR 自动执行 6 个 job：项目自检 ×2（**Windows PowerShell 5.1 与 pwsh 7 各跑一遍**）、
仓库规范（私有文件与换行符）、JS 语法门禁 + WXML 事件绑定交叉校验（ubuntu runner）、
gitleaks 密钥扫描、主包体积（上限 2 MB）。

> 为什么要跑两个 PowerShell 版本：本地开发用 5.1，CI 用 7，
> 而两者的 .NET 运行时不同、可用程序集也不同。
> 之前只跑 7，`check.ps1` 里用了 .NET Framework 独有的 `System.Web.Extensions`，
> 结果是**本地永远全绿、CI 永远红**，而这个红已经连续存在了 3 个 commit ——
> 一个检查自己坏了却没人发现的检查，等于没有检查。

> 两个版本是拆成两个独立 job 跑的，不是 matrix。
> matrix 写法（`shell: ${{ matrix.shell }}` + `if: matrix.shell == 'pwsh'`）
> 会被 GitHub 判为无效 workflow：整个 run 起不来，0 个 job，
> 而 run 名会从 `CI` 退化成文件路径——不读日志根本看不出是哪里错了。

</details>

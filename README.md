## 一、它想解决什么问题

大多数创业复盘散落在朋友圈长图、知乎回答和关停的公众号里。三个问题：

- **搜不到** —— 没有统一结构，无法按行业、原因检索
- **传不下** —— 一篇长文服务的是作者当下的倾诉欲，不服务下一个人的检索
- **更没人看** —— 发布即沉底，没有任何分发机制

我做过真实竞品调研（[完整调研](docs/product/竞品分析.md)），三条结论：

**1. 需求在海外被验证过，形态可复制。**
[Failory](https://www.failory.com) 用结构化数据库收了 400+ 条失败创业记录，
拿到 4 万+ 邮件订阅，访谈了 200+ 位失败创始人。**它证明这个形态成立。**

**2. 国内没有形态一致的产品，但也没有需求验证。**
中文的失败复盘 100% 是长文，分布在知乎、公众号、人人都是产品经理。
没人做不等于机会，也可能说明结构化在中文语境里根本不成立。

**3. 行业教育已经完成，产品化没人做。**
CB Insights「42% 的创业公司死于没有市场需求」这个数字在中文互联网早已广泛流传。
认知有了，只是没有人把它做成可检索、可比较的产品。

### 调研里最重要的一个发现

CB Insights 在 2024 年用 431 家失败公司重做了统计，结论变了：

> **「资金耗尽」在 70% 的案例里出现，但它几乎总是最后死因，不是根本问题。**
> 真正的根因首位是产品市场匹配失败（43%）。

这直接暴露了原设计的致命缺陷：`failureReason` 是自由文本，
**70% 的复盘会写成「钱烧完了」**——数据看起来很充实，但完全无法回答
产品要回答的问题。一份全是死因的失败数据库，检索价值接近于零。

所以数据模型改成了**「根因 + 死因」两层结构**，根因用 CB Insights 的受控词表
（根因 13 项 / 死因 12 项，用用户已经认得的词降低学习成本）。

> 这一段是整个项目里**唯一**我确定做对了的东西。
> 而且它是对的方向——如果这个产品有救，救它的也是这个结构。

## 二、我是怎么把它写死的

### 2.1 我先写了产品文档，然后几乎没写代码

这是全部问题的根源，值得单独一节。

我给这个项目定的顺序是：调研 → 需求文档 → 指标体系 → 埋点方案 → PRD → 代码。
听起来很完整。实际上前四步产出的都是**关于一个还不存在的产品的主张**。

`5b9b832` 那次提交的 README 是最好的证据。它声称：

| README 里写的 | 代码里实际的 |
|:--|:--|
| 「首版实现约 17 个事件、4 组」 | 事件数 **0**。`miniprogram/utils/` 是个空目录 |
| 目录树里列了 `trackEvent/` | `cloudfunctions/` 下没有这个目录 |
| 目录树里列了 `utils/track.js` | 文件不存在 |
| 数据模型表里列了 `events` 集合 | 从未被 `collection('events')` 打开过 |
| 「埋点：代码已写，**未运行时验证**」 | 一行代码都没有 |
| 「`check.ps1` 八项，含埋点事件名检查」 | 没有任何埋点相关检查 |
| 「集合数写成 5，文档另一处又写成 6」 | 代码里实际读写的：**9** 个 |
| 页面目录：**13** 个 | ✅ 这是真的 |
| 云函数目录：**8** 个 | ✅ 这是真的 |

同一份提交里，**页面数和云函数数是真的，事件数、事件通道、事件集合、
事件检查全是假的**。这种偏差比全盘造假更难被发现，因为大部分数字对得上。

而最值得记下来的是这句：

> **「代码已写，未运行时验证。」**

这七个字是我整个项目里最诚实的一句伪装。它听起来像严谨——
「我做了静态检查，只是没在真机上跑」；它的实际含义是
**这个功能一行都没写**。任何一句「待补充」「TBD」「后续完善」在这里
都是同一个意思：用模糊的严谨语气，填一个空洞。

### 2.2 界面一切正常，功能从来没工作过

第二层失败更隐蔽，因为**它连报错都没有**。

| 现象 | 根因 | 怎么发现的 |
|:--|:--|:--|
| 浏览量永远是 0 | 客户端执行 `update({views: _.inc(1)})`，而 `projects` 的写权限是「仅创建者」——A 用户看 B 用户的项目时必然被拒，错误被 `try/catch` 吞成一行日志 | 读权限配置时才想到去核对调用方 |
| 点赞数漂移，甚至变成负数 | 先插 `likes` 文档再更新计数，两个请求不在一个事务里；`_.inc(-1)` 在计数已错乱时能减成负数 | 看到计数为 -1 |
| 数据看板永久少 20 条 | 页面直接 `db.collection('projects').get()`，小程序端 SDK 单次上限 20 条。一个以聚合为唯一职责的页面，从第一天起算的就是错数 | 库里有 100 条，看板写 20 |
| 首页「全部」等于随机顺序 | 「全部」标签按 `views` 排序，而 `views` 恒为 0 | 注意到顺序每次都不一样 |
| 搜索搜不到最该搜到的 | 关键词只匹配标题，而 P0 用户的真实表达是**问题描述**而不是标题 | 读自己的投稿，发现正文和标题是两回事 |

共同点：**每一个都能正常渲染、正常点击、正常返回**。
`views` 字段在数据库里真实存在，类型是 number，值是 0。
没有任何一处会报错，也没有任何一处会「看起来不对」。

> 这是我得到的第一个教训：
> **一个功能「没报错」和「在工作」之间没有任何关系。**
> 我所有的验证都停在「没报错」，而它恰好证明不了任何事。

### 2.3 我写了一套检查，然后它坏了三个 commit 都没人告诉我

最讽刺的一段，也是这个仓库现在唯一还亮着的东西的来历。

我给项目写了 `check.ps1`（项目自检）并接进 CI。它从**第一个 commit 起就是红的**，
而我在本地看到它一直是**绿的**。原因：

```powershell
Add-Type -AssemblyName System.Web.Extensions   # .NET Framework 才有
```

`System.Web.Extensions` 只存在于 Windows PowerShell 5.1 的 GAC。
本地跑 5.1 → 全绿。CI 跑 `pwsh` 7（.NET 运行时）→ `Add-Type` 抛
「找不到程序集」→ 脚本因 `$ErrorActionPreference = 'Stop'` 当场终止 → job 失败。

**而这个红持续了 3 个 commit。** 没人发现，因为它看起来像「项目有问题」，
不像「检查本身有问题」。

同一类错误还有第二处：换行符检查**从来没执行过**。
`git grep` 没有匹配时返回 1，而 GitHub 的 PowerShell 包装器把 `$LASTEXITCODE`
直接当步骤退出码——于是「一个 CRLF 都没有」被判成「步骤失败」。

> 第二个教训：**一个坏掉的检查比没有检查更危险。**
> 没检查时你知道自己在裸奔；检查坏掉时你以为自己在被保护。
> 修好之后我又用 matrix 写法把整个 workflow 搞失效了 1 个 commit
> （0 个 job，run 名从 `CI` 退化成文件路径），第三次才做对。

## 三、我是怎么发现自己的

没有戏剧性。我准备在面试里讲这个项目，于是**打开代码，逐条核对 README**。

第一条对不上的是「埋点」。我以为那只是文档写得简略，
直到我去 `git ls-tree` 看那个 commit 的目录树——`miniprogram/utils/` 是空的。

然后我开始系统性地做同一件事：**每一条文档声明，都去代码里找它对应的实现。**
找出来的结果:

| 声称 | 结论 |
|:--|:--|
| 19 个埋点事件 | 全部不存在。现已补写，但**从未运行时验证** |
| 12 个云函数 | 原本 8 个。补了 4 个真实的：`trackEvent` / `recordInteraction` / `getStatistics` / `updateProfile` |
| 11 个集合 | 原本 9 个被读写。`events` / `project_views` 是新增的 |
| 3 个安全漏洞可利用 | 越权提权、订单一建即发权益、伪造站内通知。**全部真实可利用** |
| 「3 个漏洞**已修复**」 | 其中一个**没修好**。见下 |

### 3.1 我说「已修复」的那个漏洞，其实是开放的

把 `updateProfile` 改成三字段白名单之后，我在 `SECURITY.md` 里把越权提权
标成了「已修复」。理由在当时听上去很充分：

> 资料修改走 `updateProfile` 云函数，只接受 `nickname` / `bio` / `avatarUrl`，
> `isVip` 只能由支付回调写。

后来为了给这份 README 核实每一个数字，我把 `users` 集合的**所有客户端写入点**
全列了出来——只有一处，在 `app.js`：「查不到用户就自己 `add` 一条」的兜底。
正因为有这一处，`users` 必须配成「仅创建者可写」。

而「仅创建者可写」只回答了**谁可以写**，没回答**可以写哪些字段**。
于是这一行在调试器里执行成功：

```js
db.collection('users').doc(自己).update({ isVip: true })   // 永久会员
```

白名单管的是「走哪个入口」，权限管的是「能不能绕过入口」。**我做了前者，漏了后者，
然后写下「已修复」。**

真正的修法是把 `users` 整个锁成客户端不可写，代价是删掉 `app.js` 那段兜底
（建号只留 `login` 云函数一条路径）。

修完顺手把「客户端到底在写哪些集合」全列了一遍，**只有 4 个写操作**：
`favorites.add` / `favorites.remove` / `comments.add` / `notifications.update`。

那 `projects` 呢？它当时配的是「仅创建者可写」，
而它同样允许作者改自己项目的 `views`、`likes`、`status`——
**首页按浏览量排序，于是任何人都能把自己的项目刷到第一位，指标一起变脏。**
一个把「诚实度量」写在第一行的项目，不该留着这条缝。一起锁了。

我把它写成了 `check.ps1` 第 16 项，然后这项检查**当场又报出了 `projects`**：
「声明可写却没有客户端写入」。不是我事先想到的，是工具报出来的。

| | 浏览量恒为 0 | 越权提权 / 刷浏览量 |
|:--|:--|:--|
| 权限 vs 代码 | 权限**比代码严** → 客户端 `update` 被拒 | 权限**比代码松** → 客户端 `update` 放行 |
| 表现 | 数字永远不涨，界面正常 | 会员标记生效 / 指标变脏，界面正常 |
| 为什么没发现 | 错误被 `try/catch` 吞成一行日志 | 攻击者还没来 |
| 共同点 | **两边都没报错。** 权限是一层「没人验证过」的假设 | |

> 第四个教训：**我上一轮修复的证据，是我自己写的一句话。**
> 「已修复」不是结论，是一句我对自己的评价。
> 这一轮它能被推翻，只是因为我换了检查方式——
> 不再问「代码里有没有校验」，而是问「除了这个入口，还有没有别的路能走」。

`check.ps1` 第 16 项就是为这件事加的：
**枚举客户端所有写操作，逐个核对它是否落在允许清单里**，
清单以 `docs/数据模型.md` 的权限总表为唯一真源。

### 3.2 文档是最便宜的产出

### 3.2 文档是最便宜的产出

> **文档是最便宜的产出，所以它会先于代码膨胀。**
> 我不是在写文档，我是在用文档代替实现。
> 「未运行时验证」「后续完善」「暂未接入」这些措辞不是不诚实，

## 四、取舍

产品工作的主体是决定**不做什么**。当时最重要的四个判断：

| 判断 | 现在的评价 |
|:--|:--|
| **根因强制，死因也强制** | ✅ 依然对。根因可聚合是整个产品唯一站得住的价值 |
| **不做模板、不做草稿** | ❓ 未验证。结构化已经抬高投稿门槛，再加编辑态可能是压死供给的那一下 |
| **咨询与 VIP 不做首页入口** | ✅ 对。但我承认这是「知道自己没数据所以不敢投」的另一种说法 |
| **砍掉广告变现** | ✅ 对，而且现在看是唯一的正确决定 |

还有一个当时就写下来、现在仍然成立的**自我怀疑**：

> 结构化是这个产品最大的风险，不是它最大的优势。
> 它换来可检索性，代价是把作者想写的「一个故事」压成十个字段。
> 如果投稿转化率极低，说明这个取舍是错的。

这个假设被写成了 H5，证伪线是投稿转化率 2%。
**它没有数据，所以它既没被证实也没被证伪——它悬在那里。**
我把这个状态原样保留在 [用户旅程](docs/product/用户旅程.md) 里，
没有把它改写成「已验证」。

## 五、我从这次失败里学到的

不是方法论，是具体的错误，可以逐条对照：

1. **不要用「文档声称」代替「我验证过」。** 我写了一句
   「代码已写，未运行时验证」，这句话是我整个项目里最贵的 11 个字。
2. **`get()` 成功不等于功能可用。** 浏览量、点赞、数据看板全部
   「正常返回」，返回值全是错的。验证要问「这个数字对不对」，
   不是「有没有报错」。
3. **聚合和计数不该在客户端做。** 小程序端 SDK 单次 20 条的上限，
   让我从第一天起就在展示错数，而且它一直显示得很正常。
4. **权限配置要按「谁能写」逐个集合设计，不是全局设一套。**
   浏览量恒为 0 的根因就是「仅创建者」和「任何人可读」这两个需求冲突，
   而我没在设计时发现冲突。
5. **先写文档会让人误以为自己已经做了。** 文档的完成感是假的。
6. **检查自己也会坏。** 而且坏掉的检查不会通知任何人。
7. **诚实的数据缺失 > 漂亮的数据编造。** 我删掉了商业化文档里
   「首年 50 万、次年 250 万」的预测，因为它没有任何推导过程。
   留着它，我连「其他地方写的是不是真的」都没法确认了。

## 六、这个仓库现在是什么

功能上：13 个页面 + 12 个云函数，**可运行**；11 个集合，
根因／死因两层已落地；6 个 CI job 全绿。

但**它依然是个失败的产品**，下面这些没变：

| # | 没做完的事 | 后果 |
|:--|:--|:--|
| 1 | `events` 集合**没有任何查询界面** | 数据进了库也看不到，北极星指标**算不出来** |
| 2 | 搜索关键词**只匹配标题** | P0 用户最需要的检索恰好搜不到 |
| 3 | 搜索走 `db.RegExp` 全量匹配，结果 50 条硬截断无分页 | 库过 50 条后用户会遇到「明明有却搜不到」 |
| 4 | 无内容审核、举报、评论删除 | 涉及企业与个人负面判断，风险由平台承担 |
| 5 | 支付未接入，订单只到 `pending` | 商业化三条线全部不可用 |
| 6 | 埋点未运行时验证，`TRACK_SALT` 未配置 | 19 个事件的可信度等于没验证过的代码 |
| 7 | 演示数据初始化函数仍在云端 | 靠 `ALLOW_SEED_DATA` 闸门挡住 |
| 8 | 隐私政策、用户协议、社区规范未产出 | 微信审核必备，也因此**根本没法提审** |

第 1 和第 2 条是我最想修但没时间修的：
**一个算不出北极星指标的产品，和一个搜不到核心内容的产品，
都不值得谈上线。** 我选择先把文档和代码对齐，是因为错误的实现比缺失的实现更难发现。

2. 开通云开发，记下环境 ID（改 `miniprogram/app.js` 的 `wx.cloud.init` 的 `env`）
3. 云开发控制台新建 **11 个集合**：
   `projects` `users` `comments` `likes` `favorites` `events`
   `project_views` `notifications` `orders` `advisors` `consultations`
4. **按表设权限，不要全用同一套**：`projects` / `users` / `events` / `likes` /
   `orders` / `advisors` / `consultations` / `project_views` 设为客户端不可写，
   `notifications` 按 `recipientId` 过滤。详见
   [部署指南 §五](docs/部署指南.md#五配置数据库权限)
5. 右键 `cloudfunctions/<函数名>` → 上传并部署：云端安装依赖（**12 个函数**）
6. 给 `initTestData` 配环境变量 `ALLOW_SEED_DATA=true`（否则演示数据初始化会被拒绝）
7. 编译运行。首页为空时 → 我的 → 底部调试工具 → 初始化测试数据

完整图文步骤见 [部署指南](docs/部署指南.md)。
演示数据是**假的**（`isDemo: true`），不代表任何真实数据。

### 技术栈

| 层 | 选型 |
|:--|:--|
| 前端 | 微信小程序原生框架（WXML / WXSS / JS），无第三方 UI 库 |

| 设计 | 复古怀旧风，棕／米／灰系，**严格不使用蓝紫色**（CI 自动检查） |

### 数据库（11 个集合）

按**谁能写**分组，而不是按功能分组——这是本项目最重要的一张表，
也是浏览量恒为 0 的教训换来的：

| 集合 | 用途 | 客户端可写 | 关键字段 |
|:--|:--|:--:|:--|
| `projects` | 项目档案 | **否** | `causeRoot` `causeSymptom` `views` `likes` `status` |
| `users` | 用户与权益 | **否** | `isVip` `vipExpireAt` `projectsCount` 均只能由云函数写 |
| `comments` | 评论 | 仅创建者 | `projectId` `content` `nickname` |
| `favorites` | 收藏记录 | 仅创建者 | `projectId` |
| `likes` | 点赞记录 | **否** | `projectId`（与计数同事务） |
| `events` | 埋点事件 | **否** | `event` `uid`（哈希）`props` |
| `project_views` | 阅读去重 | **否** | `_id` = 用户+项目+自然日 |
| `notifications` | 站内通知 | 仅本人改已读 | `recipientId` `type` |
| `orders` | VIP 订单 | **否** | `status` 恒为 `pending` |
| `advisors` | 导师 | **否** | `price`（服务端定价的唯一来源） |
| `consultations` | 咨询记录 | **否** | `originalPrice` `price` `discountApplied` |

### 自检与 CI

```bash
npm run check    # 16 项
```

其中 7 项是**防「文档声称 A、代码里是 B」**的——
也就是为了不再犯 §二 那个错：

| # | 检查 | 挡什么 |
|:--|:--|:--|
| 9 | 埋点事件名**双向**校验 | 客户端与服务端白名单不一致 → 事件被静默丢弃 |
| 10 | 云函数交叉校验 | 代码调了不存在的函数 / 存在没人调用的孤儿函数 |
| 11 | 两份 `schema.js` 哈希比对 | 云函数按目录独立部署，改一份忘另一份 |
| 12 | 集合清单 ↔ 数据模型 | 少建集合 → 部署后 `collection not exists` |
| 13 | 部署指南 ↔ 云函数与集合 | 照文档部署会漏东西 |
| 14 | README 数量声明 ↔ 实际 | 「README 少写了四个云函数」这类最伤可信度的偏差 |
| 16 | **客户端写操作 ⊆ 允许清单** | 绕过云函数直接 `update`，权限一松指标就能被伪造 |

第 16 项是最近加的，来源就是 §3.1 那个「我说已修复、其实没修好」的漏洞。
它检查的不是「有没有校验」，而是「**除了预期入口还有没有别的路能写**」——
`projects` 就是被它报出来的，不是我事先想到的。

第 12–14 项则是专门为「文档漂移」写的。**它们防的不是代码退化，
是我下一次再写出「代码已写，未运行时验证」。**

CI 每次 push 与 PR 自动执行 6 个 job：项目自检 ×2（**Windows PowerShell 5.1 与
pwsh 7 各跑一遍**）、仓库规范（私有文件与换行符）、JS 语法门禁 + WXML 事件绑定
交叉校验（ubuntu runner）、gitleaks 密钥扫描、主包体积（上限 2 MB）。

> 为什么要跑两个 PowerShell 版本：本地开发用 5.1，CI 用 7，
> 而两者的 .NET 运行时不同、可用程序集也不同。
> 之前只跑 7，`check.ps1` 里用了 .NET Framework 独有的 `System.Web.Extensions`，
> 结果是**本地永远全绿、CI 永远红**，而这个红已经连续存在了 3 个 commit。

## 七、为什么它失败了

> ## ⚠️ 这一节我留给自己
>
> 前六节全是技术事实，事实可以自己核。
> 但「这个创业为什么死」不是技术问题，而且**我不能替自己回答**。
>
> 技术上它死于 §二：文档先于实现。
> 可是绝大多数项目都是这么死的，所以那不是**这个**项目死的原因，
> 那是所有项目死的原因。真正的原因是别的——
> 时间怎么分配、当时在和什么竞争、哪个假设我当时就知道没验证却还是往下做。
>
> 我不给它编一个答案。**编出来的失败原因比空着的更难看，
> 因为它会让人以为我想清楚了。**
>
> 建议写法：「它死在 ███，而我当时的判断是 ███。」
> 一到两句就够。**写不出真话就保持留空。**

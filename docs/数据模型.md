# 数据模型

> 本文档以**代码为准**。`scripts/check.ps1` 第 12 项会双向校验：
> 代码里 `db.collection('x')` 出现过的集合必须在此收录，
> 此处记载的集合也必须真的被代码读写。改了一边不改另一边，CI 会红。
>
> 共 11 个集合。

## 一、集合总览

| # | 集合 | 用途 | 写入方 | 客户端可写 |
|:--|:--|:--|:--|:--|
| 1 | `projects` | 项目档案（核心） | **仅云函数** | 否 |
| 2 | `users` | 用户资料与权益 | **仅云函数** | 否 |
| 3 | `comments` | 评论 | 客户端 + 本人 | 仅创建者 |
| 4 | `likes` | 点赞记录 | **仅云函数** | 否 |
| 5 | `favorites` | 收藏记录 | 客户端 + 本人 | 仅创建者 |
| 6 | `events` | 埋点事件 | **仅云函数** | **否（硬约束）** |
| 7 | `project_views` | 阅读去重 | **仅云函数** | 否 |
| 8 | `notifications` | 站内通知 | **仅云函数** | 仅本人改已读 |
| 9 | `orders` | 订单 | **仅云函数** | 否 |
| 10 | `advisors` | 导师 | **仅控制台** | 否 |
| 11 | `consultations` | 咨询记录 | **仅云函数** | 否 |

「客户端可写」指集合权限规则允许客户端直连数据库写入。
凡标**否**的集合，客户端权限必须设为不可写，否则对应指标或权益可被伪造。
权限怎么设见[部署指南 · 配置数据库权限](部署指南.md#五配置数据库权限)。

### 一条贯穿全文的规则

**任何由客户端写入的集合都不是可信数据源。**

这不是洁癖。这个项目里已经有三处因为「客户端能写」而失效的东西：

| 集合 | 曾出现的问题 | 现在怎么解决 |
|:--|:--|:--|
| `projects` | 客户端 `views: _.inc(1)` 被权限拒绝，浏览量**从未涨过**，界面却正常 | 计数移到 `recordInteraction` 云函数 |

> `projects` 现在也是客户端完全不可写。这是第 16 项检查报出来的，
> 不是事先想到的：检查列出「声明可写却没有客户端写入」的集合，
> `projects` 排在第一个。
>
> 留着的后果不算严重但很讨厌——「仅创建者可写」允许作者改自己项目的
> **任意字段**，包括 `views`、`likes`、`status`。
> 于是任何人都能把自己的项目刷成 `views: 99999`，
> 首页按浏览量排序，指标也就跟着一起脏了。
> 一个把「诚实度量」写在 README 第一行的项目，不该留着这条缝。
| `users` | 调试器里 `update({ isVip: true })` 就能给自己打会员标记 | 集合权限锁成客户端完全不可写，建号与改资料只走云函数 |
| `events` | 若对客户端开放，可伪造「我读了 1000 篇」 | 走 `trackEvent` 云函数 + 事件白名单 + 服务端取身份 |

## 二、字段定义

### 1. `projects`（项目档案）

整个产品的核心表。一条记录 = 一座墓碑。

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `_openid` | String | 云开发注入 | 创建者。**客户端无法伪造** |
| `title` | String | 投稿 | 项目名，≤ 40 字 |
| `description` | String | 投稿 | 简介，≤ 200 字 |
| `industry` | String | 投稿 | 行业，取值见 `INDUSTRIES`（15 项） |
| **`causeRoot`** | String | 投稿 | **根因**，13 项受控词表，必填 |
| **`causeSymptom`** | String | 投稿 | **死因**，12 项受控词表，必填 |
| `failureReason` | String | 投稿 | 失败过程，≤ 2000 字 |
| `lessonsLearned` | String | 投稿 | 经验教训，≤ 2000 字 |
| `marketPotential` | String | 投稿 | 今天还有没有机会，≤ 500 字，可空 |
| `duration` | Number | 投稿 | 持续月数，1–3650 |
| `teamSize` | Number | 投稿 | 团队人数，1–10000 |
| `cost` | Number | 投稿 | 总投入（元），0–1 亿 |
| `tags` | Array\<String\> | 投稿 | ≤ 5 个，每个 ≤ 12 字 |
| `photos` | Array\<String\> | 投稿 | ≤ 9 张，必须是 `cloud://` fileID |
| `status` | String | 服务端 | 初始恒为 `'failed'`，仅审核流程可改 |
| `views` | Number | `recordInteraction` | 阅读数，按「用户+项目+自然日」去重 |
| `likes` | Number | `recordInteraction` | 致敬数，事务内维护，下限 0 |
| `isDemo` | Boolean | `initTestData` | 演示数据标记，正式版首页过滤 |
| `createdAt` | Date | 服务端 | 创建时间 |
| `updatedAt` | Date | 服务端 | 更新时间 |

#### 为什么根因和死因要分成两个字段

竞品调研（[竞品分析](product/竞品分析.md) 第三节）发现：
CB Insights 2024 年 431 家样本的统计里，「资金耗尽」出现在 70% 的案例中，
但它**几乎总是最后死因，不是根本问题**；根因首位是产品市场匹配失败（43%）。

所以如果只留一个自由文本的 `failureReason`，70% 的记录会写成
「钱烧完了」——数据看起来很充实，但检索价值接近于零。

分成两层之后：

- `causeSymptom`（死因）回答「最后是怎么死的」→ 12 项受控词表
- `causeRoot`（根因）回答「哪一步就注定会死」→ 13 项受控词表

两张表交叉才能得到本产品最有价值的那张表：
**死因为「资金耗尽」的记录，根因分布是什么。**
如果这张表里也全是「资金耗尽」，说明引导文案失败了
（对应[指标体系](product/指标体系.md)第三节的「死因单一化率」告警）。

#### 字段白名单

客户端页面已经校验过一遍，但**客户端校验不是安全边界**——
任何人可以跳过页面直接 `wx.cloud.callFunction` 传任意 JSON。
所以 `publishProject` / `updateProject` 各自持有一份 `schema.js`，
只接受上表中标「投稿」的字段，其余一律丢弃。

> 两份 `schema.js` 必须逐字节相同（云函数按目录独立部署，引用不了公共文件）。
> `check.ps1` 第 11 项会比对两者 SHA256。

#### 索引建议

| 索引 | 服务于 |
|:--|:--|
| `createdAt` 降序 | 首页「全部」排序 |
| `views` 降序 | 首页「热门」排序 |
| `likes` 降序 | 首页「最多致敬」排序 |
| `causeRoot` 升序 + `createdAt` 降序 | 根因筛选列表 |
| `industry` 升序 | 行业筛选 |

`db.RegExp` 关键词搜索**用不上索引**（云开发不支持对正则走索引），
这是[用户旅程](product/用户旅程.md)第三节指出的已知架构限制：
记录数过千后搜索延迟与读取配额都会成为瓶颈。

### 2. `users`（用户资料与权益）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `_openid` | String | 云开发注入 | 用户标识，登录后据此查询 |
| `nickname` | String | 用户 | 昵称，≤ 20 字 |
| `avatarUrl` | String | 用户 | 头像 URL，可空串 |
| `bio` | String | 用户 | 简介，≤ 100 字 |
| `projectsCount` | Number | 服务端 | 发布数，由 `publishProject` / `deleteProject` 增减 |
| `isVip` | Boolean | **仅支付回调** | 会员标记，咨询 8 折的唯一判据 |
| `vipExpireAt` | Date | **仅支付回调** | 会员到期时间，支付接入后启用 |
| `createdAt` | Date | 服务端 | 创建时间 |
| `updatedAt` | Date | 服务端 | 更新时间 |

#### 三个字段的写入权被刻意切走

`projectsCount` / `isVip` / `vipExpireAt` **不能由客户端写**：

- `isVip` / `vipExpireAt` → 只能由支付回调在确认到账后写。
  上一版 `createOrder` 建完订单直接置 `isVip: true`，
  等于点一下按钮就是永久会员。
- `projectsCount` → 只能由发布/删除云函数增减。
  客户端可以自己写 `projectsCount: 9999` 给自己造数据。

资料修改走 `updateProfile` 云函数，且**只接受 `nickname` / `bio` / `avatarUrl`**
三个字段的白名单。

> **但白名单本身不够，这一点是后补的。**
> 上一版只做到白名单就以为修好了，实际 `users` 的集合权限仍是「仅创建者可写」，
> 而那个权限允许本人写**任意字段**——调试器里一句
> `db.collection('users').doc(自己).update({ isVip: true })`
> 完全绕开 `updateProfile` 照样生效。
> 白名单管的是「走哪个入口」，权限管的是「能不能绕过入口」，**两者缺一不可**。
> 现在 `users` 已锁成客户端完全不可写（见[部署指南 §五](部署指南.md#五配置数据库权限)），
> 所有写入经由 `login` / `updateProfile` / `publishProject` / `deleteProject`。
> 代价是 `miniprogram/app.js` 里「查不到用户就自己 add」的兜底必须删掉——
> 留着它，集合就永远锁不死。

> `vipLevel` 字段在商业化文档里被提过，但代码中从未使用，故不在此列出。
> 未落地的字段不写进数据模型，否则又是一处「文档说 A、代码是 B」。

### 3. `comments`（评论）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `_openid` | String | 云开发注入 | 评论者 |
| `projectId` | String | 客户端 | 所属项目 |
| `content` | String | 客户端 | 评论内容 |
| `nickname` | String | 客户端 | 昵称快照，改昵称不影响历史评论 |
| `createdAt` | Date | 客户端 | 发表时间 |

客户端直写。昵称存快照而非引用 `users`，是为了让「作者后来改名」
不影响已展示的历史评论——代价是昵称不一致，属有意取舍。

### 4. `likes`（点赞记录）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `_openid` | String | 云开发注入 | 点赞者 |
| `projectId` | String | `recordInteraction` | 所属项目 |
| `createdAt` | Date | 服务端 | 点赞时间 |

**写入方只有 `recordInteraction` 云函数，客户端不可写。**

原因是上一版由客户端先 `add` 再更新计数，两个请求不是事务：
中间失败就永久不一致，而 `_.inc(-1)` 在计数已错乱时能把 `likes` 减成负数。
现在点赞与计数在同一个事务里完成，且计数带下限保护。

查询索引：`projectId` + `_openid`（详情页判「我是否点过赞」）。

### 5. `favorites`（收藏记录）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `_openid` | String | 云开发注入 | 收藏者 |
| `projectId` | String | 客户端 | 所属项目 |
| `createdAt` | Date | 客户端 | 收藏时间 |

客户端直写。收藏没有全局计数，不存在计数漂移问题，
所以不必像 `likes` 那样挪到云函数。

查询索引：`projectId` + `_openid`（取消收藏需要定位到自己的那条）。

### 6. `events`（埋点事件）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `event` | String | 客户端（白名单过滤） | 事件名，19 个之一 |
| `uid` | String | **服务端** | `sha256(salt + '\|' + openid)` 前 16 位 |
| `props` | Object | 客户端 | 事件属性，≤ 8 个键，值截断 200 字符 |
| `clientTs` | Number | 客户端 | 客户端时间戳，**仅参考，不用于统计** |
| `createdAt` | Date | **服务端** | 统计口径唯一依据 |

#### 权限：客户端完全不可写

这是全套数据模型里唯一一条「客户端一行都不能写」的**普通业务外**约束。

当前架构允许客户端直连数据库写业务集合。如果 `events` 也开放，
任何人打开调试器就能伪造「我读了 1000 篇」，
于是阅读渗透率、人均月阅读条数、次月留存率同时失效——
**一个能自己造数的指标体系等于没有指标体系。**

三重防御，缺一不可：

1. 集合权限设为不可写（[部署指南 §五](部署指南.md#五配置数据库权限)）
2. `trackEvent` 内置 `EVENT_WHITELIST`，白名单外的事件名直接丢弃
3. 身份 `uid` 一律由云函数从 `cloud.getWXContext()` 取后哈希，
   客户端传上来的任何身份字段都被丢弃

#### 三个细节

- **`clientTs` 不用于统计**。只用它的话，改手机时间就能伪造「本月活跃」。
  统计一律以服务端 `createdAt` 为准。
- **`uid` 是哈希不是明文 openid**，且同一用户跨月仍是同一个值——
  不然留存率算不出来。哈希盐配在 `TRACK_SALT` 环境变量里。
- **`props` 只收标量**。一旦开始往里塞嵌套对象，指标口径就没法验证了。

事件字典见[埋点方案](product/埋点方案.md)。

### 7. `project_views`（阅读去重）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 服务端 | **复合主键**，见下 |
| `projectId` | String | 服务端 | 被阅读的项目 |
| `day` | String | 服务端 | 自然日，`YYYY-MM-DD` |
| `createdAt` | Date | 服务端 | 首次阅读时间 |

#### 存在的理由

浏览量原本由客户端 `projects.doc(id).update({views: _.inc(1)})` 维护。
但 `projects` 的写权限是「仅创建者」——**A 用户看 B 用户的项目时必然被拒**。
旧代码用 `try/catch` 把错误吞成一行日志，结果是
**浏览量从来没有涨过，而界面看起来一切正常。**

这类「静默失败」比崩溃危险得多，所以加了这张表做显式去重：
`_id` = `sha256(openid)前16位 + '|' + projectId + '|' + day`。
同一人同一项目一天内重复进入不重复计数，重复调用直接返回 `counted: false`。

它同时把「刷量」的成本从「写个循环」提高到「每天每个项目一次」——
`recordInteraction` 只在客户端，没有可绕过的写入口。

### 8. `notifications`（站内通知）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `type` | String | 服务端 | 见下方枚举 |
| `title` | String | **服务端** | 标题，服务端模板渲染 |
| `content` | String | **服务端** | 正文，服务端模板渲染 |
| `recipientId` | String | **服务端** | 收件人，恒为调用者自己的 openid |
| `relatedId` | String | 服务端 | 关联单据 ID，可空 |
| `relatedType` | String | 服务端 | `consultation` / `order` / 空 |
| `read` | Boolean | 服务端建 / 本人改 | 已读标记 |
| `createdAt` | Date | 服务端 | 创建时间 |

`type` 枚举：`order_created`、`consultation_created`、`consultation`、
`vip_expiring`、`system`。

#### 这张表修掉的是一个高危漏洞

原实现把 `type` / `title` / `content` / `recipientId` 全部从客户端接收，且不鉴权。
任何人执行：

```javascript
wx.cloud.callFunction({
  name: 'sendNotification',
  data: { recipientId: '<别人的 openid>', type: 'system',
          title: 'VIP会员开通成功', content: '点击链接...' }
})
```

就能往任意用户的通知列表里塞一条伪造的系统消息。配合界面上带「›」的样式
（暗示可点击跳转），这是一条完整的钓鱼链路。

现在的约束：

1. `recipientId` 强制等于调用者自己的 `OPENID`——只能给自己发
2. `title` / `content` 由服务端 `TEMPLATES` 渲染，客户端**无法自定义任何文案**
3. `type` 走白名单
4. 单用户频率限制：10 分钟内最多 3 条

真正的系统通知（订单、咨询）由各自的云函数直接写库，不经过本函数——
那条路径是服务端行为，不存在伪造问题。

**客户端唯一被允许的写操作是把自己的 `read` 改成 `true`。**
收件人过滤在查询时**无条件生效**（原实现是「先探测有没有我的通知，
有才加过滤」，对零通知的新用户会列出全库所有人的消息）。

### 9. `orders`（订单）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 服务端 | 主键，同 `orderNo` |
| `orderNo` | String | 服务端 | 订单号，`crypto.randomBytes` 生成 |
| `type` | String | 服务端 | `vip` |
| `plan` | String | 客户端 | `month` / `year`，服务端查表定价 |
| `amount` | Number | **服务端** | 金额（分），来自 `PLAN_CONFIG` |
| `planName` | String | 服务端 | 套餐名快照 |
| `status` | String | 服务端 | **`pending` → `paid` / `cancelled`** |
| `vipDurationDays` | Number | 服务端 | 权益天数快照 |
| `expectedExpireAt` | Date | 服务端 | 权益到期时间快照 |
| `userId` | String | 服务端 | 下单人 |
| `createdAt` | Date | 服务端 | 创建时间 |
| `updatedAt` | Date | 服务端 | 更新时间 |

#### 当前状态：`status` 只能是 `pending`，权益不发放

支付尚未接入，因此本表**只建待支付订单，不发放任何权益**。

上一版把 `status` 直接写成 `'paid'` 并立刻置 `isVip: true`，
意味着点一下按钮就能拿到永久 VIP。这比「订单参数可伪造」严重得多——
价格本来就是服务端查表得来的（不可伪造），
真正的缺陷是**整条支付链路根本不存在**。

订单号用 `crypto.randomBytes` 而非 `Math.random`：订单号是可追溯的财务凭证，
`Math.random` 不是密码学安全的随机源。

接入支付时需要补的部分见[发布检查清单](发布检查清单.md)第三节。

### 10. `advisors`（导师）

**唯一完全由控制台维护的集合。客户端可读，不可写。**

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 云开发 | 记录 ID |
| `name` | String | 控制台 | 姓名 |
| `avatar` | String | 控制台 | 头像 URL，**可为空串** |
| `title` | String | 控制台 | 头衔，如「连续创业者，前教育科技公司创始人」 |
| `bio` | String | 控制台 | 简介 |
| `industry` | String | 控制台 | 擅长行业 |
| `tags` | Array\<String\> | 控制台 | 标签 |
| `price` | Number | **控制台（权威价）** | 咨询价格（元），**客户端不能传** |
| `rating` | Number | 控制台 | 评分，**可为空** |
| `consultCount` | Number | 控制台 | 累计咨询数 |
| `isVip` | Boolean | 控制台 | 仅 VIP 可约 |
| `status` | String | 控制台 | `active` / 下架 |
| `sort` | Number | 控制台 | 排序权重 |
| `isDemo` | Boolean | `initTestData` | 演示数据标记 |
| `createdAt` / `updatedAt` | Date | 控制台 | — |

**`price` 是本表最重要的一列。** 原 `createConsultation` 里
`const { advisorId, advisorName, price } = event` 三项全信客户端，
构造一次调用即可 `price: 0` 下单。定价是商业模式的底线，
不能由购买方决定。现在姓名与定价一律从本表读。

`rating` 允许为空，页面在无值时显示 `—` 而不是默认 `5.0`——
默认 5.0 是在替导师伪造口碑。`avatar` 为空串时页面用姓氏首字占位，
因为 `<image src="">` 会渲染成裂图。

### 11. `consultations`（咨询记录）

| 字段 | 类型 | 来源 | 说明 |
|:--|:--|:--|:--|
| `_id` | String | 服务端 | `CONSULT_<时间戳>_<随机>` |
| `advisorId` | String | 客户端 | 导师 ID，服务端据此查价 |
| `advisorName` | String | **服务端** | 姓名快照，改名不影响历史单 |
| `originalPrice` | Number | **服务端** | 原价 |
| `price` | Number | **服务端** | 实付价，VIP 8 折在服务端算 |
| `discountApplied` | Boolean | 服务端 | 是否命中折扣 |
| `userId` | String | 服务端 | 预约人 |
| `status` | String | 服务端 | `pending_payment` → `confirmed` / `completed` / `cancelled` |
| `rating` | Number | — | 暂无评分入口，设计预留 |
| `createdAt` / `updatedAt` | Date | 服务端 | — |

与 `orders` 同样的口径：支付未接入，状态是 `pending_payment` 而**不是** `confirmed`，
且不创建 `orders` 记录（接入支付后由本函数补建）。

`originalPrice` / `price` / `discountApplied` 三件套的作用是：
**让「VIP 省了多少钱」在订单记录里可验证**，而不是靠客户端说。

## 三、跨集合关系

```
users ──1:N──> projects            (_openid)
projects ──1:N──> comments          (projectId)
projects ──1:N──> likes             (projectId + _openid 唯一)
projects ──1:N──> favorites         (projectId + _openid 唯一)
projects ──1:N──> project_views     (projectId，_id 内含 去重键)
advisors ──1:N──> consultations     (advisorId)
users ──1:N──> orders              (userId)
users ──1:N──> notifications       (recipientId)

（无外键约束，云开发不支持。关联靠应用层维护，
  因此删除项目时 deleteProject 必须手动清 likes/comments/favorites，
  这是当前唯一会遗留孤儿数据的地方。）
```

### 已知的数据完整性缺口

诚实列出，不假装没有：

| 缺口 | 现状 | 后果 |
|:--|:--|:--|
| `project_views` 不随项目删除而清理 | `deleteProject` 未处理 | 删除的项目仍有阅读去重记录，占空间但不影响指标 |
| `events` 不随用户注销而清理 | 无注销功能 | 埋点表会持续增长，需要定期冷归档 |
| `consultations.rating` 无写入方 | 设计预留 | 字段恒为空 |
| 咨询状态无状态机校验 | 任何状态可写 | 接入支付前不影响，但接入后必须补 |
| 评论无审核、无删除入口 | 无 | 内容合规风险，见[发布检查清单](发布检查清单.md) |

## 四、性能与容量

| 集合 | 增长来源 | 预估 1 年 | 应对 |
|:--|:--|:--|:--|
| `events` | 19 个事件 × 全部用户 | 最快，日增万级 | 超过 30 天冷归档；分页聚合而非全表扫 |
| `projects` | 人工投稿 | 慢，千条级 | 已建 5 个索引 |
| `project_views` | 每日阅读 | 中 | `_id` 天然去重，体积可控 |
| `comments` / `likes` / `favorites` | 用户互动 | 中 | 按 `projectId` 建索引 |
| `notifications` | 服务端写入 | 慢 | 有 10 分钟频率限制兜底 |
| `orders` / `consultations` | 下单 | 极慢 | 无压力 |

云开发单集合容量上限 5 GB、集合数上限 100 个、单文档 1 MB。
当前 11 个集合离上限都很远，**真正的瓶颈是读取配额（每日 5 万次/环境），
不是存储**。`getStatistics` 因此做了 `MAX_SCAN = 2000` 的扫描上限，
超出会返回 `truncated: true` 让前端提示，而不是假装给的是全量。

## 一、北极星指标

> **月度有效复盘被阅读数**
> Monthly Valid Post-Mortem Reads（MVPR）
>
> 定义：统计月内，**根因字段非空**且被详情页阅读**至少一次**的复盘记录条数。

### 为什么是它

候选指标与淘汰理由：

| 候选 | 淘汰理由 |
|:--|:--|
| 累计发布数 | 纯供给侧虚荣指标。1000 条无人阅读的记录，价值为 0 |
| 月活用户 MAU | 与产品价值无因果关系。打开即走的 MAU 也是 MAU |
| 浏览量 PV | 可被单用户刷高，且不区分内容质量 |
| 周活跃贡献者数 | 只衡量供给，不管有没有人消费，方向单一 |
| **月度有效复盘被阅读数** | **同时要求「库里有货」和「货被消费」，且带质量门槛** |

核心判断依据是这个产品的问题定义：

> 失败复盘散落在长文里，**搜不到、传不下、更没人看**。
> 问题出在「没人看」，所以指标必须盯消费侧，不是供给侧。

发布数是驱动指标，不是北极星。

### 「有效」的必要性

这个指标内置了一个质量门槛：**根因字段非空**。

如果只看阅读数，一堆空洞记录被点开也算数。加上「根因非空」后，
被计数的必须是**真正承载了可复用判断**的记录。

这个门槛直接来自[竞品分析](竞品分析.md)的发现：自由文本的失败原因会让
70% 的记录退化成「钱烧完了」这种无信息量表述。根因字段是受控词表，
填了它才说明记录有分析价值。

### 为什么按「记录数」而非「阅读次数」计

按次数计，会奖励深读单条内容，掩盖「库里 800 条只有 3 条有人看」的真相。
按去重记录数计，逼迫产品把整个库都推到用户面前——这才是内容型产品该做的事。

深度交给支撑指标「单条复盘被读次数」去衡量。

## 二、指标树

```
                 月度有效复盘被阅读数 (MVPR)   ← 北极星
                          │
        ┌─────────────────┼─────────────────┐
        │                                   │
   供给侧驱动                            消费侧驱动
   （让库里有货）                        （让货被看到）
        │                                   │
  ├ 新增有效复盘数                   ├ 复盘阅读渗透率
  ├ 有效复盘累计总量                 │  = 被读记录数 / 总记录数
  ├ 供给转化率                       ├ 人均月阅读条数
  │  = 发布成功 / 进入发布页         ├ 搜索使用率
  └ 内容结构完整率                   ├ 搜索成功率
  │  = 三段式填写完整记录 / 总量     │  = 有结果搜索 / 总搜索
                                    └ 次月留存率
```

支撑指标清单：

| 分组 | 指标 | 计算式 | 数据来源事件 |
|:--|:--|:--|:--|
| 供给 | 新增有效复盘数 | 统计月内新增且根因非空 | `publish_success` |
| 供给 | 供给转化率 | `publish_success` / `publish_start` | 两个事件 |
| 供给 | 内容结构完整率 | 失败原因+教训+市场判断三段齐全 / 新增总数 | `publish_success` 属性 |
| 消费 | 复盘阅读渗透率 | 被读去重记录数 / 总记录数 | `project_view` / `projects` 集合 |
| 消费 | 人均月阅读条数 | MVPR / 当月活跃用户数 | `project_view` / `app_launch` |
| 消费 | 搜索使用率 | `search_submit` 用户数 / 活跃用户数 | `search_submit` |
| 消费 | 搜索成功率 | 返回结果数 > 0 的搜索 / 总搜索 | `search_submit` 属性 |
| 留存 | 次月留存率 | 上月活跃用户中本月仍活跃的比例 | `app_launch` |
| 互动 | 致敬率 | `project_like` / `project_view` | 两个事件 |
| 互动 | 评论率 | `comment_submit` / `project_view` | 两个事件 |
| 互动 | 分享率 | `share_click` / `project_view` | 两个事件 |
| 传播 | 分享带来的阅读 | 落地页 `entry=from_share` 的阅读数 | `project_view` 的 `entry` 属性 |
| 商业 | 咨询下单转化率 | `order_submit` / `consult_page_view` | 两个事件 |
| 商业 | VIP 转化率 | `vip_order_submit` / `vip_page_view` | 两个事件 |

商业指标**不是**北极星。付费只是价值真实性的旁证——
一个没人看但能下单的产品，不算成功。

## 三、健康度与反向指标

只盯增长指标会掩盖质量问题。以下指标用于**发现异常**，达成阈值时触发干预。

| 指标 | 定义 | 阈值 | 触发动作 |
|:--|:--|:--|:--|
| **死因单一化率** | `causeSymptom` 填写为单一资金类症状的记录占比 | > 30% | 根因字段未强制，或词表设计有误导 |
| 灌水率 | 发布 7 天后仍为 0 阅读 0 互动的记录占比 | > 20% | 供给质量下滑，需收紧审核 |
| 搜索无结果率 | 返回 0 条结果的搜索占比 | > 30% | 词表覆盖不足，或库太小 |
| 支付校验通过率 | 订单通过官方支付校验的比例 | < 100% | **存在伪造订单，属安全问题** |
| 重复投稿率 | 相似度超阈值的新增记录占比 | > 10% | 存在批量灌水 |
| 反馈入口点击但未落地 | `debug_entry_click` 有量 | > 0 | 调试入口残留在正式版 |

**死因单一化率**是最值得盯的一个。它把竞品分析里的理论发现
（70% 案例会退化成「钱烧完了」）变成一个可监控的运营指标：
一旦这个比例升高，说明用户不理解「根因」和「死因」的区别，
需要改的是引导文案和词表设计，不是数据本身。

**支付校验通过率**低于 100% 是安全告警，不只是运营指标。
当前代码的订单创建未接官方支付校验（见[发布检查清单](../发布检查清单.md)），
上线前必须修复。

## 四、明确不追踪的指标

这部分和指标定义同样重要。列出「不做什么」比列「做什么」更能说明判断力。

| 不追踪 | 理由 |
|:--|:--|
| 注册用户数 | 产品是静默登录，无注册动作，数字无意义 |
| 总浏览量 PV 作为成功指标 | 可被单用户刷高，不区分内容质量 |
| 用户停留时长 | 消费的是结构化信息，不是长内容，停留短不代表体验差 |
| 发布数作为北极星 | 供给侧指标，见上文 |
| 分享次数作为北极星 | 分享是结果不是目的，且容易刷 |
| 付费金额作为北极星 | 会诱导把产品做成纯卖课 |

不追踪停留时长这一条需要说明：常规内容产品会用停留时长做体验指标，
但本产品的消费形态是「检索 → 快速获取判断 → 离开」。
停留时间短恰恰可能是**做对了**——用户拿到了他要的答案。

## 五、数据可信度设计

指标的可信度取决于采集通道。两条设计决定：

### 1. 埋点走云函数，客户端不可直接写

当前客户端能直接 `db.collection('users').add()` 写库。
如果 `events` 集合同样对客户端开放，任何人打开调试器就能伪造
「我读了 1000 篇」——所有指标同时失效，且无法察觉。

因此埋点单独走 `trackEvent` 云函数，`events` 集合权限设为
**所有用户可读、任何客户端不可写**。

代价是每个事件多一次云函数调用（首版为控制延迟，仅在关键节点埋点，
非全量页面曝光）。这是有意的取舍，理由是**指标可信 > 采集完整**。

### 2. 身份处理

`openid` 属敏感标识。事件表中不落明文 openid，
仅保留用于去重的会话标识与 `openid` 的哈希值。

## 六、目标设定

以下为**设定值，非实测值**。项目未上线，这些数字是待验证的假设，
上线后按实际基线校准。

| 阶段 | 目标 | 用途 |
|:--|:--|:--|
| 冷启动期 | 有效复盘 100 条，MVPR ≥ 30 | 验证供需匹配是否成立 |
| 冷启动期 | 复盘阅读渗透率 ≥ 30% | 验证「结构化」是否真的提升消费 |
| 第 3 个月 | MVPR ≥ 100，次日留存 ≥ 20% | 验证是否有自然增长 |
| 第 3 个月 | 死因单一化率 ≤ 30% | 验证根因引导设计是否有效 |

**冷启动期最关键的不是 MVPR，是渗透率。**
如果 100 条记录里只有 3 条被读过，说明内容型产品的价值假设不成立，
应该停下来重新想定位，而不是继续加大供给。

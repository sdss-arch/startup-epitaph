# 埋点方案

> 状态：**代码已实现，未运行时验证**。项目未部署，因此本文档描述的是
> 采集设计，不是实测结果。事件字典中的每个名字都已在代码里落地，
> `scripts/check.ps1` 第 9 项做双向校验（白名单 ↔ 服务端 ↔ 实际调用点）。
>
> 19 个事件，分 5 组。

## 一、为什么要先解决「零埋点」

原稿写完了指标体系，却没有采集能力。这是产品文档里最常见的一种自欺：
**指标写不出来不代表指标成立，只代表还没人去看。**

而这件事的优先级不能靠「顺手加上」来定。本产品最核心的判断是
[用户旅程](用户旅程.md) 里的 H5：

> H5：贡献门槛是可接受的。
> **证伪信号：供给转化率低于 2% 则结构化取舍已被证伪。**

这条假设决定了产品成立与否。要检验它，就必须能算出「进入发布页的人里
有几个人发布成功了」。所以埋点的第一版不追求覆盖，只追求
**把「供给转化率」和「MVPR」这两条主链路的分子分母都埋齐**。

## 二、三层设计

### 层 1：客户端封装（`miniprogram/utils/track.js`）

```javascript
const track = require('../../utils/track.js');

track.setContext({ industry: '电商' });   // 页面级公共属性
track.track('project_view', { projectId: id });
track.once('publish_start', { entry: 'tabbar' });
track.flush();                            // 切后台时强制上报
```

四个函数，对应四个真实需求：

| API | 用途 |
|:--|:--|
| `track(event, props)` | 上报一次 |
| `once(event, props)` | **单次会话内**去重。用于「进入发布页」这类只需计一次的口径 |
| `setContext(extra)` | 设置后续事件的公共属性，页面 `onLoad` 调一次 |
| `flush()` | 立即上报队列全部事件。`app.onHide` 里调 |

**批量与合并**：逐条 `callFunction` 在低端机上能明显拖慢首屏。
队列攒够 5 条或最多等 8 秒再一次性上报。

**三条硬约束：**

1. **永不影响主流程**。上报失败、队列满、云端超时，一律静默丢弃。
   指标少一条可以接受，页面挂掉不可接受。`track()` 内部不抛错。
2. **客户端不上报 openid**。用户身份由云函数从 `cloud.getWXContext()` 取。
3. **队列上限 50 条**。防止用户狂点时无限堆积占内存。

开发期还有一条自检：事件名不在 `TRACK_EVENTS` 内时 `console.warn` 并丢弃。
拼错事件名是埋点最常见的错误，而静默丢弃会让它到看报表时才发现。

### 层 2：云函数通道（`cloudfunctions/trackEvent/`）

```
客户端队列 → trackEvent 云函数 → events 集合（客户端不可写）
```

为什么必须走云函数：当前架构允许客户端直连数据库写业务集合。
若 `events` 也开放，任何人打开调试器就能伪造「我读了 1000 篇」，
于是阅读渗透率、人均月阅读条数、次月留存率**同时失效且无法察觉**。
一个能自己造数的指标体系等于没有指标体系。

四道限制：

| 限制 | 值 | 挡什么 |
|:--|:--|:--|
| 集合权限 | 客户端不可写 | 伪造任意事件 |
| 事件白名单 | 19 项 | 上报不存在的名字，污染指标字典 |
| `MAX_BATCH` | 20 | 构造 1 万条把集合打爆 |
| `MAX_PROPS` / `MAX_VALUE_LEN` | 8 键 / 200 字符 | 超长文本撑爆文档 |

### 层 3：数据约束

| 约束 | 做法 | 挡什么 |
|:--|:--|:--|
| 身份 | `uid = sha256(TRACK_SALT + '\|' + OPENID)` 前 16 位 | 伪造他人阅读记录；明文 openid 落库 |
| 时间 | 统计一律用服务端 `createdAt`，`clientTs` 仅参考 | 改手机时间伪造「本月活跃」 |
| 属性类型 | 只收 string / number / boolean | 嵌套对象让口径无法验证 |
| 失败语义 | 云函数 catch 后返回 `{ ok: true, accepted: 0 }` | 埋点异常冒泡到用户面前 |

## 三、事件字典

**属性类型**：`s` = string，`n` = number，`b` = boolean。

### 组 1 · 消费（5 个）

服务[指标体系](指标体系.md)里的「复盘阅读渗透率」「人均月阅读条数」「搜索使用率」。

| 事件 | 上报时机 | 属性 | 服务指标 |
|:--|:--|:--|:--|
| `app_launch` | `app.onLaunch` | `launchMode`(s) 冷/热启动场景值 | 次月留存率、人均月阅读条数的分母 |
| `project_view` | 详情页数据加载成功后 | `projectId`(s) `entry`(s) `industry`(s) `causeRoot`(s) | **MVPR（北极星）**、阅读渗透率、致敬率/评论率/分享率的分母 |
| `search_submit` | 搜索执行完成（无论有无结果） | `keyword`(s) `hasKeyword`(b) `industry`(s) `causeRoot`(s) `resultCount`(n) `success`(b) | 搜索使用率、**搜索成功率**、搜索无结果率 |
| `search_result_click` | 点中某条搜索结果 | `projectId`(s) `causeRoot`(s) `position`(n) | 搜索质量（点第几位命中） |
| `root_cause_filter` | 切换行业或根因筛选 | `dimension`(s) `cause_root`/`industry`；`value`(s) | **H1 验证**：根因维度是否真被使用 |

`project_view` 的 `causeRoot` 属性是关键——它让
「哪些根因的复盘更值得看」可以被直接算出来，而不只是「总共有多少阅读」。

`root_cause_filter` 独立成一个事件而不是塞进 `search_submit` 的属性，
是因为它服务的是**另一个假设**（H1：用户痛点是检索而非信息缺失）。
混在一起就看不出「用户到底用不用根因筛选」。

### 组 2 · 互动（5 个）

| 事件 | 上报时机 | 属性 | 服务指标 |
|:--|:--|:--|:--|
| `project_like` | 点赞成功后 | `projectId`(s) `causeRoot`(s) | **致敬率**（H3 验证） |
| `project_favorite` | 收藏成功后 | `projectId`(s) | 复访率 |
| `comment_submit` | 评论入库成功后 | `projectId`(s) `length`(n) | **评论率** |
| `share_click` | 点右上角转发菜单 | `projectId`(s) `channel`(s) `chat`/`timeline`；首页分享无 `projectId`，带 `from`(s) | **分享率**、分享带来的阅读 |
| `notification_click` | 点开一条通知 | `type`(s) `wasUnread`(b) | 召回有效性 |

分享事件只在**用户真的点了菜单**时上报，不在 `onShareAppMessage` 里无条件上报——
`onShareAppMessage` 是回调，触发时机与用户意图不完全等价。

`project_like` 只在成功后报。失败也报的话，致敬率会分母膨胀，
而失败恰恰是最需要知道的情况——所以失败另外走 `console` 与 toast，不进指标。

### 组 3 · 供给（4 个）

**这 4 个事件是整个埋点里最重要的一组。** H5 是最可能被证伪的假设，
供给侧没有这组事件就无法检验。

| 事件 | 上报时机 | 属性 | 服务指标 |
|:--|:--|:--|:--|
| `publish_start` | 发布页 `onLoad`，**用 `once()`** | `entry`(s) `tabbar`/`navigate` | **供给转化率的分母** |
| `publish_success` | 云函数返回成功后 | `industry`(s) `causeRoot`(s) `causeSymptom`(s) `hasMarketPotential`(b) `photoCount`(n) `filledFields`(n) | **供给转化率的分子**、内容结构完整率、**死因单一化率** |
| `publish_abandon` | 离开发布页且已填过字段 | `filledFields`(n)；一进一出时附 `reason`(s) `immediate_exit` | 门槛诊断（填到第几个字段放弃） |
| `publish_error` | 校验失败 / 服务端报错 / 网络异常 | `stage`(s) `validation`/`server`/`network`；`reason`(s) `filled`(n) | 投稿可用性 |

`publish_abandon` 带的 `filledFields` 是这组事件里最有信息量的一个属性：
它能回答「用户是在看到第 3 个字段时放弃，还是在写完 9 个字段后放弃」——
这两个结论指向完全不同的产品动作（减字段 vs 改引导）。

`publish_error.stage = 'validation'` 占比高，说明字段约束太严；
`stage = 'network'` 占比高，说明是服务端问题而不是产品设计问题。
这两者的处理方式完全不同，所以必须分开。

**编辑页刻意不上报埋点。** `edit-project` 的成功不计入 `publish_success`：
19 个事件是按漏斗设计的，把编辑混进发布会让「供给转化率」的分母错乱
（编辑的人一定是发过帖的人，混进来等于把同一个用户数两次）。
编辑相关行为目前只在 `console` 里记录。

### 组 4 · 商业（4 个）

| 事件 | 上报时机 | 属性 | 服务指标 |
|:--|:--|:--|:--|
| `consult_page_view` | 咨询页 `onLoad` | `source`(s) | 咨询下单转化率的分母 |
| `order_submit` | 咨询下单成功 | `type`(s) `advisorId`(s) `amount`(n) `paid`(b) | 咨询下单转化率的分子 |
| `vip_page_view` | VIP 页 `onLoad` | `entry`(s) 当前选中套餐 | VIP 转化率的分母 |
| `vip_order_submit` | VIP 订单创建成功 | `plan`(s) `amount`(n) `paid`(b) | VIP 转化率的分子 |

`paid` 属性**当前恒为 `false`**。支付未接入，订单只到 `pending` 状态。
它被显式记下来而不是省略，是为了将来接入支付时能直接对比
「下单转化率」与「支付转化率」的差——那个差就是支付流程的流失。

商业指标不是北极星，理由见[指标体系](指标体系.md)第二节：
付费只是价值真实性的旁证，一个没人看但能下单的产品不算成功。

### 组 5 · 诊断（1 个）

| 事件 | 上报时机 | 属性 | 服务指标 |
|:--|:--|:--|:--|
| `debug_entry_click` | 点调试工具的任一按钮 | `action`(s) `init`/`reset` | **健康度告警**（见下） |

这是唯一一个**有量就是 bug** 的事件。

[指标体系](指标体系.md)第三节定义了一条健康度阈值：

> 反馈入口点击但未落地：`debug_entry_click` 有量 → 阈值 > 0 →
> 触发动作「调试入口残留在正式版」。

即：**正式版里它的期望值是 0**。任何一条记录都说明调试入口没被隔离。
当前代码用 `app.isProduction()`（`globalData.env === 'production'`
或 `envVersion === 'release'`）隐藏入口。

放这个事件而不是不埋，是为了让它在灰度期可观测——
灰度期间如果入口没隔离，会有人点，需要事后能查出来。

## 四、哪些地方**故意没埋**

列出来和列出做了什么同样重要。

| 没埋 | 理由 |
|:--|:--|
| 页面曝光（PV） | 明确不追 PV 作为成功指标。逐页曝光会让上报量翻数倍而换不来新判断 |
| 停留时长 | [指标体系](指标体系.md)第四节：消费形态是「检索→拿到判断→离开」，停留短可能恰是做对了 |
| 滚动深度 | 同上，且 WXML 监听滚动在小程序端性能开销明显 |
| 崩溃 / 错误上报 | 需要接微信自带的「小程序错误监控」，不该自己造一套 |
| 编辑项目行为 | 会污染供给转化率，见组 3 说明 |
| 订单支付结果 | 支付未接入，没有真实的 `paid` 时刻可埋 |
| `users` 表的任何变化 | 服务端字段变更不是用户行为，不该混进行为数据 |

## 五、身份处理

```
uid = sha256(TRACK_SALT + '|' + OPENID).slice(0, 16)
```

`recordInteraction` 里的阅读去重键用**同一个算法**（盐相同时），
所以两套数据的用户维度可以对齐。

### 为什么是哈希而不是明文

- `openid` 是敏感标识，事件表是行为数据，两者混在一张表里扩大泄露面
- 哈希后仍能按用户聚合（留存率、去重阅读），但无法反查身份

### 为什么必须是同一个值跨月稳定

留存率的计算式是「上月活跃用户中本月仍活跃的比例」。
如果 `uid` 每次都变（加随机盐或用时间戳），这个指标恒等于 0，
而且**不会报错**——只会显示「本项目留存率为 0」。
这类静默错误比崩溃更难发现。

### 盐的配置

```bash
# 云函数 → trackEvent → 配置 → 环境变量
TRACK_SALT=<一个随机字符串>
```

未配置时退化为 `APPID`，保证 clone 下来就能跑，但削弱了不可逆性
（`APPID` 是公开信息）。**上线前必须配置。**

同一套盐也应配到 `recordInteraction`，否则两套数据的用户维度对不上。

### 一条不能做的事

**不要为了「方便 join」把 `openid` 明文塞进 `props`。**
`sanitizeProps` 不会拦它（它只拦嵌套对象和超长值），
但这会让整个身份设计失效。当前代码没有任何地方这样做，
这属于「靠纪律而不是靠机制」的边界——如果要更稳，
下一步应该加一条 `props` 键名黑名单（`openid` / `unionid` / `openId`）。

## 六、口径约定

| 约定 | 理由 |
|:--|:--|
| 统计时间窗一律用服务端 `createdAt` | `clientTs` 可被改手机时间伪造 |
| 去重口径：阅读按「用户+项目+自然日」，`project_view` 埋点不去重 | 埋点要的是「意图次数」，业务计数要的是「有效次数」，两者本就该不同 |
| 事件名一旦发布不改名 | 改名等于清空历史序列。改语义也要**新增**事件名而不是改旧的 |
| 属性只增不删不解释 | 改一个属性的含义会让历史数据变成错误数据 |
| 漏斗事件成对出现 | `X_start` / `X_success` / `X_abandon` / `X_error`，缺一环就算不出转化率 |

### `props` 的形状

`setContext` 设的公共属性与事件自带属性在云函数里**合并成扁平结构**：

```javascript
props: Object.assign({}, sanitizeProps(item.ctx), sanitizeProps(item.props))
```

扁平化是为了能直接按 `causeRoot` 聚合，
嵌套结构在云开发控制台里没法一眼筛出来。

## 七、上线前必须做的三件事

| # | 事项 | 不做的后果 |
|:--|:--|:--|
| 1 | 配置 `TRACK_SALT` 环境变量（`trackEvent` 与 `recordInteraction` 都配） | 身份哈希退化为用公开 `APPID` 加盐，可逆性丧失 |
| 2 | 确认 `events` 集合权限为「所有用户可读，**所有用户不可写**」 | 整套指标可被任意伪造且无法察觉 |
| 3 | 确认正式版 `debug_entry_click` 恒为 0 | 健康度告警形同虚设 |

验证第 2 条的方法：在调试器里执行
`wx.cloud.database().collection('events').add({data:{event:'project_view'}})`，
必须报权限错误。

## 八、当前状态与已知缺口

| 项 | 状态 |
|:--|:--|
| 事件名与调用点一致 | ✅ `check.ps1` 第 9 项校验 |
| 客户端/服务端白名单一致 | ✅ 同上 |
| 集合权限收紧 | ⚠️ **需人工在控制台确认**，无法由代码保证 |
| `TRACK_SALT` | ⚠️ 未配置，退化为 `APPID` |
| 运行时验证 | ❌ **未部署，未跑过一次真实上报** |
| 数据看板 | ❌ `events` 集合**没有任何查询界面** |

最后一条是当前最大的缺口：数据进了库，但**还没有页面能看到它**。
这意味着现在还无法回答「北极星指标现在是多少」。
补一个内部用的数据查询页是上线前的前置工作，
见[发布检查清单](../../docs/发布检查清单.md)。

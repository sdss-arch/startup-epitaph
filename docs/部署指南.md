## 二、创建云开发环境

1. 打开微信开发者工具，导入本项目
2. 工具栏点击 **云开发**
3. 点击 **开通**，填写环境名称（例如 `创业墓志铭`）
4. 记下生成的**环境 ID**，形如 `cloud1-xxxxxxxx`

> 环境 ID 在下一步要用到。创建后不会频繁变动，但重建环境会导致小程序无法访问旧数据。

## 三、修改项目配置

本仓库为了让 clone 即可编译，保留了**占位符**配置。**你必须改成自己的**：

### 3.1 小程序 AppID

`project.config.json`：

```json
{
  "appid": "wx0000000000000000"
}
```

替换为你的小程序 AppID。修改后建议不要将该文件回退，避免误提交他人 AppID。

### 3.2 云环境 ID

`miniprogram/app.js` 第 12 行：

```javascript
wx.cloud.init({
  env: 'cloud1-xxxxxxxx',   // ← 换成你的环境 ID
  traceUser: true
});
```

### 3.3 运行环境标记

`miniprogram/app.js` 的 `globalData.env`：

```javascript
globalData: {
  env: 'development'   // 上线前改为 'production'
}
```

这个值控制调试工具入口的显示。`app.isProduction()` 除了读它，
还会读 `envVersion === 'release'`，所以正式版即使忘了改也不会漏。

> 这两个占位符不会触发 `check.ps1` 的密钥扫描
> （`wx0…` 与 `cloud1-x…` 被识别为占位符），但换成真值后**必须**换成自己的，
> 否则 `npm run check` 会报「疑似微信 AppID / 云开发环境 ID」。

## 四、创建数据库集合

云开发控制台 → **数据库** → **添加集合**，依次创建 11 个：

| 集合名 | 用途 | 字段定义 |
|:--|:--|:--|
| `projects` | 项目档案（核心） | 详见 [数据模型](数据模型.md) |
| `users` | 用户资料与权益 | 同上 |
| `comments` | 评论 | 同上 |
| `likes` | 点赞记录 | 同上 |
| `favorites` | 收藏记录 | 同上 |
| `events` | 埋点事件 | 同上 |
| `project_views` | 阅读去重 | 同上 |
| `notifications` | 站内通知 | 同上 |
| `orders` | 订单 | 同上 |
| `advisors` | 导师 | 同上 |
| `consultations` | 咨询记录 | 同上 |

**为什么是 11 个而不是 5 个**：前 5 个是业务表，后 6 个是后来补上的——
埋点通道（`events`）、浏览量去重（`project_views`，因为客户端改不了别人的
`views`）、通知，以及商业化的三张表。少建任何一个，对应页面会直接报
`collection not exists`。

**建索引**（`projects` 集合，可选但强烈建议）：

| 字段 | 方向 | 服务于 |
|:--|:--|:--|
| `createdAt` | 降序 | 首页「全部」排序 |
| `views` | 降序 | 首页「热门」排序 |
| `likes` | 降序 | 首页「最多致敬」排序 |
| `causeRoot` | 升序 | 根因筛选 |
| `industry` | 升序 | 行业筛选 |

其余集合建议索引：`comments`/`likes`/`favorites` 的 `projectId`，
`notifications` 的 `recipientId`，`project_views` 不需要（`_id` 就是查询键）。

创建步骤：

1. 输入集合名称
2. 确定
3. 点击刚创建的集合
4. 进入 **权限设置**（见第五节）
5. 按第五节的表设置权限，**不要全部用同一套**
6. 重复以上步骤创建其余 10 个

## 五、配置数据库权限

权限设置是本项目**最容易出错、后果最严重**的一步。

**这里只有两类权限，不是全部都设成「仅创建者可写」。**
`events` / `orders` / `advisors` 等集合如果开放客户端写，
对应的指标和权益就能被任何人伪造——这不是理论风险，是可以直接在调试器里
执行一行代码做到的事。

### 5.1 权限总表

| 集合 | read | write | 说明 |
|:--|:--|:--|:--|
| `projects` | `true` | `false` | **客户端完全不可写**（见 5.2） |
| `users` | `true` | `false` | **客户端完全不可写**（见 5.2 第 4 行） |
| `comments` | `true` | `doc._openid == auth.openid` | 同上 |
| `favorites` | `true` | `doc._openid == auth.openid` | 同上 |
| `notifications` | `doc.recipientId == auth.openid` | `doc.recipientId == auth.openid` | **按收件人过滤**，不按 `_openid` |
| `likes` | `doc._openid == auth.openid` | `false` | **客户端完全不可写** |
| `events` | `true` | `false` | **客户端完全不可写**（硬约束） |
| `project_views` | `false` | `false` | 纯服务端，无客户端读写需求 |
| `orders` | `doc.userId == auth.openid` | `false` | **客户端完全不可写** |
| `advisors` | `true` | `false` | 仅控制台维护 |
| `consultations` | `doc.userId == auth.openid` | `false` | **客户端完全不可写** |

### 5.2 五个「客户端完全不可写」的集合为什么必须锁死

| 集合 | 锁死后谁写 | 不锁的后果 |
|:--|:--|:--|
| `events` | `trackEvent` 云函数 | 伪造「我读了 1000 篇」，全部消费侧指标同时失效 |
| `orders` / `consultations` | 各自的云函数 | 伪造订单，污染收入数据；当前状态机也无校验 |
| `likes` | `recordInteraction` 云函数 | 计数与文档不一致，`_.inc(-1)` 能把 `likes` 减成负数 |
| `users` | `login` / `updateProfile` / `publishProject` / `deleteProject` | **给自己打会员标记**：`update({ isVip: true })` |
| `projects` | `publishProject` / `updateProject` / `deleteProject` / `recordInteraction` | 作者可改自己项目的 `views` / `likes` / `status`，指标和首页排序一起变脏 |

后两行是后补的，值得单独说：

`users` 原本配的是「仅创建者可写」，理由是「本人可以改自己的资料」。
但**「仅创建者可写」不等于「只能改资料」**——它允许本人写**任意字段**，
于是 `db.collection('users').doc(自己).update({ isVip: true })` 直接生效。
`updateProfile` 的三字段白名单拦不住它：白名单管的是「走哪个入口」，
而调试器里可以完全绕开这个入口直接调数据库。

`projects` 是同一个毛病，只是后果没那么刺激：作者可以给自己的项目写
`views: 99999`。它**不是事先想到的，是被 `check.ps1` 第 16 项报出来的**——
检查列出「声明可写却没有客户端写入」的集合，它排在第一个。

> 这是本项目第二次栽在同一类问题上：
> **代码层做了校验，不等于权限层做了约束。**
> 第一次是浏览量——客户端 `update` 被权限拒绝，错误被 `try/catch` 吞掉，
> 浏览量永远是 0。两次的方向正好相反：
> 一次是权限比代码严，一次是权限比代码松。

因此建号与投稿路径必须唯一：`users` / `projects` 的所有写入都经由云函数，
客户端只读不写。`miniprogram/app.js` 里那段「查不到就自己 add」的兜底
正是 `users` 必须开放写的原因，已删除。

> 锁死之后，全项目客户端只剩 **4 个**写操作：
> `favorites.add` / `favorites.remove` / `comments.add` / `notifications.update`
> （仅改自己的已读状态）。这 4 个由 `check.ps1` 第 16 项持续盯着。

控制台里对应的「权限设置」选项：
**所有用户可读，仅创建者可写** / **所有用户可读，所有用户不可写** /
**仅创建者可读写**。若控制台只提供「自定义规则」，
按上表填 JSON 即可，语法与 `read`/`write` 字段一致。

> `_openid` 由云开发自动注入，客户端无法伪造，因此以它为条件的规则是可信的。
> `orders` / `consultations` / `notifications` 用的是自己写的 `userId` /
> `recipientId` 字段——**这三个字段也必须由云函数写**，
> 因为客户端可以给自己塞一个 `recipientId: '别人的openid'`。
> 当前代码里它们都只由云函数写入。

### 5.3 验证权限配置 ⚠️

部署完成后逐项实测。这一步不能跳——权限配错时不会报错，
只会「看起来一切正常」。

**用两个不同微信账号 A / B 登录，确认：**

| 验证项 | 期望结果 |
|:--|:--|
| A 读取 `projects` 中 B 的项目 | ✅ 能读 |
| A 修改 B 的项目 | ❌ 权限错误 |
| A 修改**自己**的项目（`views` / `status` 也不行） | ❌ 权限错误 |
| A 写 `events` | ❌ 权限错误 |
| A 读 `orders` 中 B 的订单 | ❌ 查不到 |
| A 读 `notifications` 中 B 的通知 | ❌ 查不到 |
| A 写 `advisors` | ❌ 权限错误 |
| A 改自己的 `users.isVip`（控制台或调试器执行 `update`） | ❌ 权限错误 |
| A 点赞后退出重进 | ✅ 点赞状态保持，`likes` 计数不重复累加 |

**前两项通过但后三项没测过，等于没测。**
写权限配错是最容易漏的，因为它只影响特定账号的特定操作。

## 六、部署云函数

1. 右键点击函数文件夹
2. 选择 **上传并部署：云端安装依赖**

需部署的 12 个函数：

| 函数 | 作用 | 必需 |
|:--|:--|:--|
| `login` | 静默登录换取 openid | ✅ |
| `publishProject` | 发布项目（字段白名单校验） | ✅ |
| `updateProject` | 更新项目（同上） | ✅ |
| `deleteProject` | 删除项目 | ✅ |
| `recordInteraction` | 阅读计数与点赞（服务端） | ✅ |
| `getStatistics` | 数据看板聚合 | ✅ |
| `updateProfile` | 改资料（字段白名单） | ✅ |
| `trackEvent` | 埋点写入通道 | ✅ |
| `sendNotification` | 站内通知 | ✅ |
| `initTestData` | 灌入演示数据 | ✅（上线前停用） |
| `createOrder` | 创建 VIP 订单 | 商业化 |

## 七、配置云函数环境变量

两个云函数需要环境变量，否则功能不完整。

| 云函数 | 变量 | 取值 | 不配的后果 |
|:--|:--|:--|:--|
| `initTestData` | `ALLOW_SEED_DATA` | `true` | 演示数据初始化**永远失败**（这是有意的闸门） |
| `trackEvent` | `TRACK_SALT` | 任意随机串 | 身份哈希退化为用公开 `APPID` 加盐 |
| `recordInteraction` | `TRACK_SALT` | **与 `trackEvent` 相同** | 两套数据用户维度对不齐 |

设置方式：云开发控制台 → 云函数 → 该函数 → 配置 → 环境变量。

`ALLOW_SEED_DATA` 是一道**运行时闸门**，不是权限控制——
微信小程序没有「仅服务端可调用」的云函数，任何人知道函数名就能直接调。
所以 `initTestData` 靠这个变量变成空壳，正式发布时把它去掉。

`TRACK_SALT` 建议用一条随机字符串即可（不需要高强度，因为攻击者拿不到
`OPENID` 明文以外的任何东西，但也不要用 `123456`）。

2. 滚动到页面底部

> ⚠️ **若提示「演示数据初始化未开放」**，说明第七步的 `ALLOW_SEED_DATA`
> 环境变量没配。这是预期行为，不是 bug。

> 「死因单一化率」这个健康度指标也会失真。

## 十一、常见问题

### `database collection not exists: projects`

数据库集合未创建。回到第四步，确认 11 个集合都已创建且名称完全一致。

### 云函数调用失败

1. 确认云函数已「上传并部署：云端安装依赖」
2. 确认 `app.js` 中的 `env` 与实际环境 ID 一致
3. 在开发者工具 → 云开发 → 云函数 → 日志中查看具体报错

### 静默登录无响应

基础库版本低于 2.2.3 会导致 `wx.cloud` 不可用。检查 `project.config.json` 中的
`libVersion`，并确认控制台无报错。

### 图片上传失败

云存储未开通。云开发控制台 → **存储** → 开通。

### 演示数据看不到

1. 确认 `projects` 与 `advisors` 集合都已创建
2. 确认 `initTestData` 已部署
3. 确认集合权限**不是**「仅创建者可读写」——演示数据的 `_openid` 属于云函数上下文，
   必须用「所有用户可读」才能在列表里看到

### 演示数据初始化未开放

`initTestData` 的 `ALLOW_SEED_DATA` 环境变量没配。见第七步。

### 浏览量一直是 0

多半是 `recordInteraction` 没部署成功。检查云函数日志里有没有
`collection not exists: project_views`。

（历史上这个 bug 更隐蔽：老代码在客户端 `update({views: _.inc(1)})`，
被 `projects` 的权限规则拒绝后用 `try/catch` 吞掉了，**界面一切正常但计数从未上涨**。
现在计数在服务端，失败会直接报错。）

### 数据看板数字看着不对

检查 `getStatistics` 是否部署。它有 `MAX_SCAN = 2000` 的扫描上限，
超出会返回 `truncated: true`，页面应提示「统计已截断」而不是假装是全量。

### 如何重置演示数据

我的 → 底部调试工具 → **重置并重新初始化**。

弹窗文案是「将删除全部演示数据并重新写入。你自己发布的项目不受影响」——
**这个措辞与实际行为一致**。`deleteOld` 只清理 `isDemo: true` 的记录，
不会 `where({}).remove()` 把真人投稿一起清掉。

### 提交了别人的 AppID 怎么办

`git rm --cached project.config.json` 将其移出索引，
加入 `.gitignore`，然后在本地重建该文件。

## 十二、正式发布

1. **移除调试工具**（见[发布检查清单](发布检查清单.md)）
2. **配置 `TRACK_SALT`**，并从 `initTestData` 移除 `ALLOW_SEED_DATA`
3. 微信公众平台配置：名称、简介、图标、类目、用户隐私保护指引
4. 接入微信支付（如启用商业化），配置商户号、API 密钥、支付证书、回调地址
5. 提交审核
6. 通过后发布

> 小程序支付需要 ICP 备案，咨询服务涉及相关资质，详见
> [商业化 · 合规提示](商业化.md#六合规提示)。

# 发布检查清单

上架前逐项确认。**带 ⚠️ 的项目若未处理，会造成数据泄露、资金损失或指标失效。**

本文档的每一项都能对应到一处代码或一个文档，
不是为了凑数的仪式清单。清单上打勾但代码没改，等于没打勾。

## 一、必须停用 ⚠️

### 1. 移除调试工具入口

`miniprogram/pages/profile/profile.js` 与 `profile.wxml` 中的
**调试工具**区块包含「初始化测试数据」和「重置并重新初始化」按钮。

**当前状态：已做运行时隔离，但需要最后一步人工确认。**

`app.isProduction()` 在 `globalData.env === 'production'`
或 `envVersion === 'release'` 时返回 `true`，入口随即隐藏。

⚠️ **两个字段是「或」关系**，所以即使忘了改 `globalData.env`，
正式版（`release`）也不会漏。仍建议把 `env` 改成 `'production'`——
它同时是体验版（`trial`）的保护。

**门禁是否真的生效，看埋点里有没有数据：**

> `debug_entry_click` 有量 → 阈值 > 0 → **调试入口残留在正式版**

这是[指标体系](product/指标体系.md)第三节的健康度告警。
发布后第一件事就是查这个事件：

```
db.collection('events').where({ event: 'debug_entry_click' }).get()
```

有任何一条记录都说明门禁失效，需要立刻排查。

### 2. 删除 `initTestData` 云函数 ⚠️

即使前端入口已移除，云函数仍可被直接调用——
**微信小程序没有「仅服务端可调用」的云函数**，
任何人只要知道函数名就能 `wx.cloud.callFunction` 调它。

**从云端删除该函数**，并从仓库中移除 `cloudfunctions/initTestData/`。

**两道闸门必须都做：**

| 闸门 | 做法 | 挡住什么 |
|:--|:--|:--|
| 运行时 | 移除 `ALLOW_SEED_DATA=true` 环境变量 | 函数变成空壳，任何调用都返回失败 |
| 部署 | 从云端删除函数目录 | 彻底不存在 |

只做第一道，函数仍在云端、仍会被调用（只是失败）；
只做第二道，仓库里留着一个可被误部署的函数。**两道都要做。**

### 3. 支付校验 ⚠️

**当前状态：支付未接入，订单只到 `pending`，权益不发放。**

代码层面已经做到「不接支付就不给权益」——
`createOrder` 不再写 `status: 'paid'`，也不再置 `isVip: true`。
所以**现在不接支付是安全的**。

上线时二选一：

- [ ] **保持现状**：把 `vip` / `consulting` 页面的购买按钮置灰或标注「支付功能开发中」
- [ ] **接入支付**：按[商业化 · 接入支付需要补的部分](商业化.md#四接入支付需要补的部分)做完 5 件事

若选择接入，以下为硬要求：

- [ ] 订单状态**只能**由支付回调 `payNotify` 改写
- [ ] 回调校验 `out_trade_no` 与金额一致
- [ ] 回调幂等：同一 `out_trade_no` 只发放一次权益
- [ ] 权益发放逻辑抽为独立函数，由 `payNotify` 复用
- [ ] 订单状态机校验（当前任何状态都可写）
- [ ] 退款流程

**判断标准**：如果审核时有人能证明「不付款也能获得会员权益」，
这一项就是没做完。

## 二、配置核查

### 4. 确认使用的是自己的 AppID

`project.config.json` 中的 `appid` 必须是你自己的。
仓库里是占位符 `wx0000000000000000`，`check.ps1` 不会报错（占位符被豁免）。

`miniprogram/app.js` 的 `wx.cloud.init({ env: '...' })` 同理，
占位符是 `cloud1-xxxxxxxx`。

### 5. 确认云环境 ID

`miniprogram/app.js` 中的 `env` 必须指向你的环境，
且该环境已开通云存储。

### 6. 配置 `TRACK_SALT` ⚠️

| 云函数 | 变量 | 状态 |
|:--|:--|:--|
| `trackEvent` | `TRACK_SALT` | 未配置时退化为用 `APPID` 加盐 |
| `recordInteraction` | `TRACK_SALT` | **必须与 `trackEvent` 相同** |

`APPID` 是公开信息，用它当盐等于没有盐。
两处不一致则埋点数据与业务数据的用户维度对不齐。

### 7. 数据库权限复查 ⚠️

**这是最容易出错、后果最严重、且配错时不会报错的一步。**
权限错配的表现是「界面一切正常，但数据是假的」。

逐个集合确认（云开发控制台 → 集合 → 权限设置）：

| 集合 | read | write | 配错的后果 |
|:--|:--|:--|:--|
| `projects` | 所有用户可读 | 仅创建者可写 | 开放写 = 可改别人的项目、注入 `views` |
| `users` | 所有用户可读 | 仅创建者可写 | **开放写 = 自己给自己打 `isVip`，咨询 8 折白拿** |
| `comments` | 所有用户可读 | 仅创建者可写 | 开放写 = 可删别人的评论 |
| `favorites` | 所有用户可读 | 仅创建者可写 | 开放写 = 可操纵他人收藏 |
| `notifications` | **按 `recipientId` 过滤** | 仅本人 | 配成「所有用户可读」= **可列出全库所有人的站内通知** |
| `likes` | 仅创建者可读 | **所有用户不可写** | 开放写 = 计数漂移，`likes` 可被减成负数 |
| `events` | 所有用户可读 | **所有用户不可写** | **开放写 = 整套指标可伪造，全部消费侧指标同时失效** |
| `project_views` | 所有用户不可读 | 所有用户不可写 | 开放写 = 可伪造阅读去重 |
| `orders` | 仅本人可读 | **所有用户不可写** | 开放读 = 可列出他人订单 |
| `advisors` | 所有用户可读 | **所有用户不可写** | 开放写 = 可把自己改成 ¥0 导师 |
| `consultations` | 仅本人可读 | **所有用户不可写** | 同上 |

**实测方法**：用两个不同微信账号 A / B 分别登录，逐项确认：

- [ ] A 能读 B 的项目
- [ ] A 改 B 的项目 → 权限错误
- [ ] A 写 `events` → 权限错误
- [ ] A 读 `orders` 中 B 的订单 → 查不到
- [ ] A 读 `notifications` 中 B 的通知 → 查不到
- [ ] A 写 `advisors` → 权限错误
- [ ] A 改自己 `users.isVip` → 无效

**只测前两项等于没测**——后五项才是容易被漏配的部分。

### 8. 清理演示数据

演示数据由 `initTestData` 写入，一律带 `isDemo: true` 标记。

- [ ] 确认首页在正式版过滤掉 `isDemo` 记录
- [ ] 正式库中不残留演示数据（控制台搜索 `isDemo: true` 逐条确认或批量删）

**注意**：演示数据带**真实的** `views` / `likes` 数值（最高 1540）。
如果混进正式数据，数据看板的总浏览/总致敬会从第一天就是错的。
`getStatistics` 当前**不过滤** `isDemo`，所以这一步必须人工做。

### 9. 埋点运行时验证 ⚠️

代码已实现但**从未真实上报过一次**。上线前必须验证：

- [ ] 进一次首页 → `events` 集合出现 `app_launch`
- [ ] 点开一个项目 → 出现 `project_view`，`uid` 非空且为 16 位十六进制
- [ ] 同一 `uid` 在两条不同事件的记录里**相同**（证明哈希稳定，留存率才算得出来）
- [ ] `createdAt` 是服务端时间，不是客户端时间
- [ ] 切后台再回来，队列已 flush（`app.onHide` 里调了 `flush()`）
- [ ] 断网时全流程仍可用（埋点静默失败，不影响页面）
